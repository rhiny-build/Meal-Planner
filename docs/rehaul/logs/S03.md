# S03 — Recipe book and agent-run schema

## Built
- One additive migration, `add_recipe_book_and_agent_run_tables`. The app looks and behaves exactly as before; nothing in the UI reads the new columns yet.
- `Recipe` gets `kind` (default `full`, so every existing recipe is `full`), `servings`, `description`, `totalTimeMinutes`, `notes`.
- New `RecipeStep` table (method steps, each with an optional timer). A recipe with no steps is normal.
- `Ingredient` gets a numeric `amount` for servings scaling. `quantity` and `unit` stay as the free-text fallback.
- New `AgentRun` and `AgentStep` tables so S05 (and later agents) can record every run.
- `lib/ingredientAmount.ts`: `parseAmount(quantity, unit)` turns "1 1/2 pounds" into 1.5 (or null when unsure).
- `lib/recipeStepTokens.ts`: the `{ing:<id>}` token helpers for step text.
- `prisma/backfillIngredientAmounts.ts`: fills `amount` for existing ingredients; runs in `npm run build` right after `migrateIngredients`.

## Decisions
- **Strings, not Postgres enums** for `kind`, `status`, `trigger` and step `kind`, like the rest of the schema (`tier`, `source`, `type`). Easier to extend additively; the allowed values are documented in schema comments.
- **Token format: `{ing:<ingredientId>}`**, id characters `[A-Za-z0-9_-]` (cuid fits). Unknown/deleted ids render as the plain words "the ingredient" (`UNKNOWN_INGREDIENT_TEXT`), malformed fragments like `{ing:` or `{ing:}` are left in the text untouched, and nothing ever throws. A bad scale (NaN, 0, negative) falls back to 1.
- **A token renders as amount + unit + name** ("Sift 300 g flour"), because cook mode text reads naturally that way; if an ingredient has no numeric `amount`, its free-text quantity is shown unscaled.
- **Backfill is a script, not SQL inside the migration.** The parser is TypeScript and unit-tested; duplicating it in SQL would diverge. The script is idempotent, only sets `amount` where it is null, never changes `quantity`/`unit`, and uses raw SQL so `updatedAt` is not bumped (verified: after the backfill the Recipe and Ingredient rows are byte-identical on every pre-existing column). It runs on every Vercel build (cheap, no-op once done), so ingredients created after deploy by the existing routes get an `amount` on the next deploy. It supports `--dry-run` and `--list` (prints the quantities that stayed null) for the production dry-run report.
- **Parser is conservative.** Parses: `2`, `1/2`, `1 1/2`, `1.5`, `½`, `1½`, `500g`, `500 g`, `1 1/2 pounds`, `1/4 cup`, `2 Large`. Leaves null: ranges (`2-3`, `2 to 3`), sums (`2 + 1/2`), words (`a pinch`, `to taste`, `some`), `0`, negative, zero denominators, unknown trailing words (`1 can (400g)`, `2 xyzzy`), and any disagreement between a unit embedded in the quantity ("500g") and the unit field ("cups"). It only reads the quantity text and the unit field; it never changes them. The unit the parser finds inside the text (e.g. `g` from "500g") is returned by `parseAmount` but is not written to the DB, to avoid showing "500g g" in the shopping list.
- **No unique constraint on `(recipeId, order)` / `(runId, order)`**, only indexes: it keeps reordering and re-saving steps simple (no transient clashes). Callers must write contiguous 0-based orders.
- **AgentRun token totals**: `inputTokens`, `outputTokens`, `cacheReadTokens`, `cacheCreationTokens` (all `Int` default 0). `AgentStep` has nullable `inputTokens`/`outputTokens` (only model steps fill them).
- **Cascades**: deleting a recipe deletes its steps; deleting an AgentRun deletes its steps. `AgentStep.payload` is `Json` so S05 can store model content, tool input or tool output without further migrations.
- **Legacy `Recipe.ingredients` text column untouched.** `recipeUrl` untouched.
- **Old test fixtures** typed as `Recipe` / `Ingredient` got the new fields added so `tsc` stays clean (no production code needed changing; the existing API routes return the new columns automatically).
- Integration tests: `tests/integration/setup.ts` `clearTestDatabase` now also clears `AgentRun`. Env note: the `.env.test` URL points at the `postgres` user; this session ran integration tests with `TEST_DATABASE_URL`/`DATABASE_URL`/`DATABASE_URL_UNPOOLED` pointed at a local `mealplanner_test_s03` database.

## How it works
Design: recipes were a name plus a text blob of ingredients, with a structured `Ingredient` table beside it. S03 adds the pieces a "cook now" experience and an agent need, without changing what exists. Steps point at ingredients by id so the same step text can show 300 g or 450 g depending on servings. Agents write a run log as a header row plus ordered step rows.

```
Recipe ──< Ingredient        (name, quantity "1 1/2", unit "pounds", amount 1.5)
  │  kind full|quick, servings, description, totalTimeMinutes, notes
  └──< RecipeStep            (order, text "Sift {ing:abc}", timerSeconds?)

AgentRun ──< AgentStep       (order, kind model|tool_call|tool_result, toolName?, payload Json, tokens?)
  agent, trigger, input, status, output?, error?, startedAt, finishedAt?, token totals
```

**Why steps reference ingredients by id.** If the step said "add 200 g flour" as plain text, scaling to 6 servings would mean parsing prose. With `Add {ing:abc}`, the step stays fixed and cook mode looks up ingredient `abc`, multiplies its `amount` by `servings wanted / recipe servings`, and prints "Add 300 g flour". Renaming flour to "plain flour" or editing its amount never breaks the method. If someone deletes the ingredient, the step shows "Add the ingredient" instead of crashing.

Two pieces of code matter:

```ts
// lib/ingredientAmount.ts: only return a number when the text is unambiguous
parseAmount('1 1/2', 'pounds')  // { amount: 1.5, unit: 'pounds' }
parseAmount('500g', null)       // { amount: 500, unit: 'g' }
parseAmount('2-3')              // { amount: null, unit: null }  -> stays free text

// lib/recipeStepTokens.ts
renderStepText('Whisk {ing:abc} with milk.', recipe.structuredIngredients, 2)
// -> 'Whisk 400 g flour with milk.'
validateStepText(text, ingredientIds)  // { valid, unknownIds, malformed }
```

**What the agent-run tables hold for one example run** (restock agent reading a receipt):
- `AgentRun`: `agent = "restock"`, `trigger = "manual"`, `input = {receiptId: ...}`, `status = running`, `startedAt`. At the end: `status = succeeded`, `output = {proposals: [...]}`, `finishedAt`, and the summed token counts.
- `AgentStep` rows, in order: `0 model` (Claude decides to look something up, `payload` = the response content, token usage filled), `1 tool_call` (`toolName = search_master_list`, `payload = {query: "milk"}`), `2 tool_result` (same `toolName`, `payload = {matches: [...]}`), `3 model` (final answer, token usage), and so on. Reading the steps in `order` replays what the agent did.

## Handoff
- **Token format** is `{ing:<ingredientId>}`. Helpers in `lib/recipeStepTokens.ts`: `makeIngredientToken`, `parseStepText` (segments), `getStepIngredientIds`, `renderStepText(text, ingredients, scale)`, `describeIngredient`, `formatAmount`, `validateStepText(text, validIds)`, constant `UNKNOWN_INGREDIENT_TEXT`. S04/S06 should call `validateStepText` before saving steps (reject unknown ids), and pass `scale = wantedServings / recipe.servings` to `renderStepText`.
- **Parser**: `parseAmount(quantity, unit)` in `lib/ingredientAmount.ts`. New-ingredient write paths (create/update routes, URL import, S04's recipe editor, MCP `create_recipe`) should call it so `amount` is set on save; today the routes do not, and the build-time backfill fills `amount` on the next deploy. Cook mode must fall back to the free-text `quantity` when `amount` is null (`describeIngredient` does).
- **Run logging (S05)**: create an `AgentRun` (`status` defaults to `running`), append `AgentStep` rows with contiguous 0-based `order`, then update the run with `status`, `output` or `error`, `finishedAt` and token totals. Allowed values: trigger `manual | batch | schedule | mcp`; status `running | succeeded | failed`; step kind `model | tool_call | tool_result`. These are plain strings, not DB-enforced.
- **Recipe `kind`**: `full | quick`. Use `where: { kind: 'quick' }` etc. Meal-plan slot logic is unchanged.
- **Neon backup before merging** (PLAN rule for schema PRs): create `backup/<YYYYMMDD>-S03`. The build runs `migrate deploy` then the two data scripts; on a fresh Neon branch both are idempotent.
- Parallel sessions (S04, S05, S06) must not touch `prisma/schema.prisma`; everything they need is here.
