# S06 — MCP upgrade for recipe discovery from Claude.ai

## Built
- From Claude.ai you can now ask for a recipe, say "save it", and it lands in the book with method steps (with timers), servings, kind (full or quick), description, total time and notes.
- Claude can read one recipe in full (`get_recipe`) and change an existing one (`update_recipe`): e.g. describe a family recipe and have the method added.
- `get_recipes` now shows each recipe's `kind`, `has_method` and `servings` (no steps, to keep the list small).
- Ingredients get a numeric `amount` (via S03's `parseAmount` when only free text is sent), and step references become `{ing:<id>}` tokens, so cook mode (S08) can scale them.
- The old `create_recipe` shape (name, `ingredients[{name, quantity}]`, `metadata`) still works unchanged.
- No schema change.

## Decisions
- **Step reference syntax: `{ing:N}`, N = 1-based position in the submitted ingredient list.** 1-based because that is how a model counts a list. A purely numeric reference is always a position; real ids are cuids and never purely numeric, so the two cannot clash. Out-of-range positions (0, or larger than the list) are rejected with a message naming the step, and nothing is saved. Real ids are also accepted if they belong to the recipe, which lets `get_recipe` output be sent back unchanged.
- **`get_recipe` returns both forms of each step:** `text` (rendered with amounts, for showing the user) and `text_with_references` (raw tokens, to send back to `update_recipe`). Ingredients carry `position` and `ingredient_id`.
- **Ingredient input:** `name`, optional `amount` (number), `unit`, `quantity` (free text, legacy), `notes`. If `amount` is given and no `quantity`, `quantity` is filled with the formatted number. If only `quantity` is given, `parseAmount(quantity, unit)` fills `amount` (null when unsure, as in S03). The legacy `Recipe.ingredients` text column is written as "quantity unit name" lines (and regenerated when ingredients are replaced).
- **`update_recipe` semantics:** a patch. Omitted = unchanged, `null` = clear (servings, description, totalTimeMinutes, notes, metadata fields). `steps` and `ingredients` REPLACE the whole list (`steps: []` removes the method). Everything runs in one transaction, so a bad reference changes nothing (tested).
- **Replacing ingredients while keeping the old method:** deleting ingredients changes their ids, which would orphan tokens in the kept steps. The server re-points each token to the new ingredient with the same name (case-insensitive); if the ingredient was dropped, the token becomes its plain name ("salt"), never a dangling id. If Claude sends new steps too, they are resolved against the new ingredients instead.
- **Errors are returned, not thrown:** `{success:false, error}` plus MCP `isError: true` (the old tool returned success:false without the flag). Validation by zod at the MCP layer (positive ints, `kind` enum `full|quick`).
- **Tier is `new`** for everything created through MCP (unchanged). `metadata.source` still maps to `recipeUrl` (unchanged quirk; it can hold a URL or a name). `tags` from the old spec were never implemented and still are not.
- **Handlers are exported functions** (`createRecipeHandler`, etc.) separate from `registerX`, so they can be unit-tested with a mocked Prisma. A shared module `lib/mcp/recipeInput.ts` holds schemas, ingredient-row building, step resolution and result helpers.
- **No duplicate-name guard in code.** The tool descriptions tell Claude to check `get_recipes` first and use `update_recipe` if the recipe exists. Adding a server-side guard seemed a UX decision (what if he wants two versions?), so I left it.
- **The route has no authentication** (see Handoff). I did not add any: out of scope and a decision for Ronen.
- Server version string bumped to 0.2.0. `docs/Specs/MCP.md` is not edited (spec file, not in my allowed list); see proposed doc updates.

## How it works
**Design.** Claude.ai is the front end: it talks, researches and cooks. The app only exposes a small set of tools over MCP at `/api/mcp`. Each tool has a name, a typed input schema and a text description. Claude reads the descriptions of all tools at the start of the conversation and decides from them (plus what the user says) which one to call and when. So the description is the behaviour: the write tools say "call only after the user explicitly confirms", define what confirmed means, and say what to check first. The code cannot know whether the user really said yes; the description is the only guard, so it is written as instructions to the model.

What the descriptions steer:
- `get_recipes` = browse and de-duplicate, read-only, does not return methods ("call `get_recipe` for that").
- `get_recipe` = read one in full; "always before `update_recipe`" so Claude edits what is really there.
- `create_recipe` = new recipe; only after "yes, save it"; check `get_recipes` first; "never invent a method: omit steps".
- `update_recipe` = change an existing one; only after Claude has told the user exactly what it will change and they agreed; send only the fields that change; `steps`/`ingredients` replace the whole list.

**Step-reference conversion.** Claude cannot know database ids before the recipe exists, so it writes steps that point into its own ingredient list: `"Whisk {ing:1} and {ing:2}"`. The server creates the ingredients first, reads back their ids in order, then rewrites each number into the real token. All in one transaction.

```ts
// lib/mcp/recipeInput.ts
const text = step.text.replace(/\{ing:(\d+)\}/g, (match, digits) => {
  const position = Number(digits)
  if (position < 1 || position > ingredientIds.length) { /* remember error */ return match }
  return `{ing:${ingredientIds[position - 1]}}`          // 1 -> first ingredient's real id
})
validateStepText(text, ingredientIds)                   // S03 helper: rejects unknown/malformed
```

```ts
// lib/mcp/tools/createRecipe.ts (inside prisma.$transaction)
const created = await tx.recipe.create({ data: { ..., structuredIngredients: { create: rows } },
                                          include: { structuredIngredients: { orderBy: { order: 'asc' } } } })
const resolved = resolveSteps(steps, created.structuredIngredients.map(i => i.id))
if (!resolved.ok) throw new Error(resolved.error)       // rolls the whole recipe back
await tx.recipeStep.createMany({ data: resolved.steps.map(s => ({ ...s, recipeId: created.id })) })
```

Later, cook mode takes `Whisk {ing:cm...}` and renders "Whisk 300 g plain flour" (scaled by servings) with S03's `renderStepText`; `get_recipe` already does the unscaled version.

**One real run (over HTTP, MCP client against `next dev` on local Postgres):**
1. `create_recipe` "E2E Fluffy Pancakes" (kind full, servings 4, 3 ingredients with amounts, 2 steps, one with a 600 s timer) returned `success:true`, 3 ingredients, 2 steps.
2. `get_recipe` returned steps like "Whisk 300 g plain flour, 400 ml milk and 2 egg." and `text_with_references` "Whisk {ing:cmv57...}, ...".
3. `create_recipe` "E2E Shini's Dal" with ingredients only (no method), then `update_recipe` with `servings: 4` and two steps referencing `{ing:1}` / `{ing:2}` returned `changed: ["servings","steps"]`; `get_recipe` showed "Rinse 250 g red lentils." and a 1200 s timer.
4. `get_recipes` listed both with `kind: full, has_method: true, servings: 4`.
5. Errors: `update_recipe` with `{ing:9}` on a 2-ingredient recipe returned `isError` with "Step 1 refers to ingredient {ing:9} ... Positions start at 1."; `get_recipe` on an unknown id returned `isError`.
6. The old-shape `create_recipe` (`quantity: "2 cups"`, `metadata.carbs`) still saved.

Tests: 24 new unit tests (`lib/mcp/recipeInput.test.ts`, `lib/mcp/tools/recipeTools.test.ts`, mocked Prisma) and 9 integration tests (`tests/integration/mcp-recipes.integration.test.ts`: a real MCP client linked in memory to the real server, real Postgres). The full unit suite is 340 passing; integration is 35 passing; `tsc --noEmit` is clean.

## Try on the preview
Preview note: the Vercel preview points at its own Neon branch (a copy of production), so recipes you save there do not touch production. The MCP connector in Claude.ai is registered against ONE URL; add a second custom connector pointing at `<preview-url>/api/mcp` (name it "Meal Planner preview") for this test, and disable the production one meanwhile so Claude does not mix them up. If the preview has Vercel deployment protection on, the connector cannot reach it; in that case test after merge against production using the recipe names below (and delete the test recipes afterwards in the app).

Exact script, in a new Claude.ai chat with the Meal Planner connector enabled. Type each line yourself:

1. "What recipes do I have with chicken? Just names, and tell me which have a method saved."
   Expect: a list from `get_recipes`; Claude can say which have a method (most old ones: none).
2. "Find me a simple, quick recipe for lemon garlic salmon for 2 people. Show it, don't save it yet."
   Expect: Claude shows the recipe and asks if you want it saved. In the connector tool-call log, `create_recipe` has NOT been called.
3. "Yes, save it as a quick recipe."
   Expect: Claude calls `create_recipe` once (kind `quick` or `full`, servings 2, with steps) and reports it saved. Open the app Recipes page on your phone: "Lemon Garlic Salmon" is there with its ingredients. (The recipe book screen is S04; if it is not merged on the preview yet, the recipe appears in the list and in Claude via step 4.)
4. "Show me the saved Lemon Garlic Salmon in full."
   Expect: `get_recipe`; Claude lists ingredients and numbered steps with amounts filled in (e.g. "Season 2 salmon fillets..."), servings 2, and any timers.
5. "Now a family one. Find 'Shini' in my recipes (any Shini's dish). Here is how it is made: <describe 4-5 steps in your own words, e.g. rinse the lentils, fry onion and spices, add lentils and water, simmer 20 minutes, finish with lemon>. Add that as the method and say it serves 4."
   Expect: Claude calls `get_recipe` first, then PROPOSES the steps back to you and asks to confirm (it should not write yet). Reply "yes, save that". Claude calls `update_recipe` once with servings 4 and steps. Ask "show me the method again": the new steps appear, and the app shows servings and the method for that recipe.
6. Negative check: "Add the method to Lemon Garlic Salmon" without giving one. Expect Claude to ask you for it rather than inventing a method and saving it.

Clean up afterwards (if on production): delete "Lemon Garlic Salmon" from the app; for the Shini's dish keep or remove the method as you like.

## Handoff
- **Tools** (`lib/mcp/tools/`): `get_recipes` (adds `kind`, `has_method`, `servings`), `get_recipe`, `create_recipe`, `update_recipe`. Shared helpers in `lib/mcp/recipeInput.ts`. S13 (MCP plan tools) can follow the same pattern: exported handler plus `registerX`, results through `jsonResult` / `errorResult`.
- **Tokens:** MCP accepts `{ing:N}` (1-based position) in submitted steps and always stores `{ing:<id>}`. S04's editor and S05's importer should store the same format; S05 could reuse `toIngredientRow` / `resolveSteps` (they are not MCP-specific).
- **Replacing ingredients changes their ids** (delete and recreate). Anything holding an ingredient id (steps via the remap above) must be re-pointed. If S04's editor saves ingredients differently (in-place update), the two paths can coexist because tokens only need valid ids.
- **SECURITY / QUESTION for Ronen: `/api/mcp` has no authentication.** Anyone with the production URL can call it. Before this session that meant reading recipes, meal plans and shopping history and creating recipes. `update_recipe` now lets any caller overwrite or wipe the method and ingredients of any recipe. The URL is unlisted and `get_recipes` makes ids easy to find for anyone who connects. I did not add auth (outside the session prompt, and claude.ai custom connectors support OAuth or a secret in the URL, which is a choice for you). Suggested minimum: a long random token path or header check from an env var (`MCP_SECRET`) before merging; I can do that as a small follow-up if you want.
- No test-only seeds or fixtures were added besides the integration test file.
- Sandbox: external sites are blocked, so no live Claude.ai call was possible from the build session; the MCP client used against the running route was the official SDK over Streamable HTTP.
