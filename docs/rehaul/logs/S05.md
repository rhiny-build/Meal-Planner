# S05 — Recipe importer agent (hand-rolled loop) and agent runs page

## Built
- **Recipes page, new "Import" button** ("Import from URL or description"). Paste a recipe link, or describe a recipe in your own words ("my schnitzel: chicken breast, flatten, egg, breadcrumbs, fry 4 min a side"). After a few seconds you get a review screen: name, kind, servings, time, ingredients (the source's own quantities), method, a "maybe the same recipe" warning if something similar is already in the book, and a link to how it was imported. **Save to recipe book** saves it (tier "new"); **Discard** saves nothing.
- A page with no method gives a recipe with no steps. A page that can't be read, or a description that isn't a recipe, gives a plain message ("Could not import a recipe: ...") instead of a made-up recipe.
- **New page `/agent-runs`** (also in the menu as "Agent Runs"): every agent run (agent, trigger, status, time, duration, steps, tokens). Tap a run to replay it step by step: what the model said and asked for, each tool call and its result (tap to expand), the final output or the error. It is generic: later agents appear there with no changes.
- The old AI import box in the recipe form is gone. The form keeps a plain "Recipe URL (optional)" field. The old `/api/recipes/extract` route, `extractIngredientsFromURL` and `components/AIImportSection.tsx` are removed. **The P1 bug "URL extraction returning wrong recipe" is superseded**: that code path no longer exists. The new importer reads the page's own recipe data (or its visible text) and checks it, rather than asking the model to guess from 15,000 characters of raw HTML.
- Code: `lib/agents/loop.ts` (the loop), `lib/agents/runLog.ts`, `lib/agents/recipeImporter/` (prompt, tools, safe fetch, page-to-text, save), `app/api/recipes/import` (+ `/save`), `app/agent-runs/`, `app/recipes/components/RecipeImportModal.tsx`.

## Decisions
- **Model and config:** the importer uses `AI_CONFIG.recipeImporter` in `lib/ai/config.ts` (model `CLAUDE_MODELS.agent`, 8000 max tokens, `maxTurns` 8). No model names elsewhere. `EXTRACT_HTML_MAX_LENGTH` (15,000) is reused as the cap on page text returned by `fetch_page`.
- **`tool_choice: auto`** in the loop (per the S01 log, `claude-sonnet-5-5` rejects forced tool choice and `thinking: disabled`). The loop sets no `thinking` option.
- **Model ends its turn without a tool call:** the loop sends one nudge ("Finish by calling the submit_recipe tool..."), recorded as a step of kind `note` in the run log (a fourth step kind beside `model`/`tool_call`/`tool_result`; S03 documented three, they are plain strings, and the runs page shows any kind). If the model does it again the run fails cleanly ("The model stopped without calling submit_recipe"). A reply cut off by `max_tokens` fails the run without running its (possibly incomplete) tool call. Neither happened in any real run; both are unit- and integration-tested.
- **Tool errors do not fail the run.** If a tool throws (bad page, invalid recipe), the loop sends the message back as a `tool_result` with `is_error: true` and Claude can retry. `submit_recipe` uses this to validate: empty name, no ingredients, duplicate or malformed ingredient keys, step tokens pointing at unknown keys (via `validateStepText` from S03), protein/carb types that are not in `DishType`.
- **A way out: `cannot_import_recipe(reason)`.** Found on a real run: with the page unreachable, the model satisfied `submit_recipe` (it requires an ingredient) with a recipe called "PLACEHOLDER - ingredients could not be imported". Now the model has an honest exit: the tool is marked `givesUp`, the loop fails the run with the model's own reason, and the UI shows it. The prompt says never to submit a placeholder or a guessed recipe. After the fix the same unreachable URL failed cleanly three times in a row.
- **Draft ingredient keys.** In a draft, step text uses `{ing:i1}` with a temporary key per ingredient (the real ids don't exist until saving). `saveRecipeDraft` creates the recipe and ingredients, then rewrites each key to the real cuid and creates the steps, in one transaction. The draft is re-validated on save (it comes back from the browser).
- **We compute `amount`, not the model.** The model supplies the quantity and unit as text exactly as the source writes them; the server fills the numeric `amount` with `parseAmount` (S03). So units are never converted silently, and "2-3" or "a pinch" stay text with `amount` null. This replaces the "amount" field in the prompt's tool description; the draft still carries `quantity`, `unit` and `amount`.
- **Source URL is set by us** (the URL typed in), not by the model.
- **`submit_recipe` does not save.** Saving is a separate route called by the review screen's Save button. Saved recipes get tier `new`, `prepTime` from the model (null if unknown), `vegetableType = 'vegetable'` if the model says vegetables are a main part, and the legacy `Recipe.ingredients` text column filled from the ingredient lines.
- **Page reading:** `fetch_page` returns the schema.org Recipe from JSON-LD when the page has one (only name, description, yield, times, ingredients, instructions: images, ratings and author are dropped) and **no page text** in that case; otherwise it returns the page's visible text (scripts, styles, nav, footer, forms removed; capped at 15,000 characters). In the real runs the JSON-LD page cost about 1,300 characters of tool output.
- **find_similar_recipes:** case-insensitive name search on each meaningful word, ranked by shared words, kept if at least half the words match, top 5. The review screen shows matches as a warning, nothing is blocked. "Lemon Garlic Salmon" showing up for "Lemon Garlic Chicken Thighs" shows the threshold is generous; it is a hint, not a duplicate detector (S07 will do real duplicate work).
- **One text box, two modes:** a lone `http(s)://...` string is a URL, anything else is a description (`classifyImportInput`). A description that contains a URL plus other text is treated as a description.
- **Security of `fetch_page` (SSRF).** The URL comes from a user and the model, so the server must not be tricked into reading its own network. `lib/agents/recipeImporter/safeFetch.ts`: http/https only; the hostname is resolved and every address must be public (blocks loopback, 10.x, 172.16-31.x, 192.168.x, 100.64/10, link-local 169.254.x incl. cloud metadata, 0.x, multicast/reserved, IPv6 equivalents and IPv4-mapped IPv6); redirects are followed by hand (max 5) and each hop is re-checked; 15 s timeout; 2 MB body cap; web page content types only. There were no protections before (the old route fetched any URL). **Dev/test flag:** `ALLOW_PRIVATE_FETCH=1` allows loopback and private addresses so local fixtures work; it is ignored when `NODE_ENV === 'production'` (Vercel production and preview both run with that), so it cannot weaken a deployed environment even if set there by mistake, and it never opens link-local/metadata addresses. Checked for real: with `NODE_ENV=production ALLOW_PRIVATE_FETCH=1` localhost, 127.0.0.1 and 169.254.169.254 are all blocked; without the flag also blocked; with `NODE_ENV=development` + flag the fixtures load. Known remaining gap: the address is checked before the request, so a hostile DNS server could answer differently the second time (DNS rebinding); closing it means pinning the connection to the checked address. Not done, noted for Ronen as low risk in a single-household app.
- **The sandbox blocks external recipe sites**, so the real runs used local fixture pages (below), served from a small HTTP server in the scratchpad. Live external URL: I tried `https://www.bbcgoodfood.com/recipes/easy-pancakes-recipe` (and curl to three other sites): the sandbox cannot reach any of them (curl gets no response; the app's fetch fails). So that attempt went through the real app as a **failure test**, not a success: the importer reported it cannot fetch the page. **No successful live-site import was possible from here**; please try one on the preview.
- **Minimal review view (S04 not merged).** `RecipeImportModal` shows a read-only draft with Save / Discard. When S04's editor lands, it should replace the review body: it takes a `RecipeDraft` (`lib/agents/recipeImporter/types.ts`) and the save route takes the (edited) draft. Likely merge conflicts with S04, all small: `app/recipes/components/RecipesClient.tsx` (an "Import" button and the modal), `components/RecipeForm.tsx` (import section removed, plain URL field added), `lib/hooks/useRecipes.ts` (exposes `refresh`), `components/Header.tsx` (one nav link).
- The "Import" button has a short label so three buttons fit on a phone; the modal title carries the full wording "Import from URL or description".
- Run records are written step by step; token totals are written at the end of the run. If the server dies mid-run, the run stays `running` with 0 tokens (the detail page says "Still running, or it stopped without finishing"). No cleanup job yet.
- `maxDuration = 120` on the import route (real runs took 3 to 16 seconds). Prompt caching is not used (runs are short); easy to add later via `cache_control` on the tools/system.

## How it works
**Design.** An agent here is a conversation with Claude where Claude may ask us to run tools. We write the rules of the conversation (the prompt), the tools, and the loop that keeps it going. The loop in `lib/agents/loop.ts` is generic: it knows nothing about recipes. The importer is just a prompt and four tools:

| Tool | What it does |
|---|---|
| `fetch_page(url)` | Safe fetch. Returns the page's schema.org Recipe (JSON-LD) if present, else its visible text. |
| `find_similar_recipes(name)` | Looks for similar names in the recipe book. |
| `cannot_import_recipe(reason)` | Honest exit: ends the run as failed with a reason. |
| `submit_recipe(recipe)` | The final answer. Checks it and returns the draft. **Does not save.** |

**The loop (`runAgent`), in plain words:**
```ts
for (let turn = 1; turn <= maxTurns; turn++) {
  // 1. ask Claude (only place the model is called), tool_choice auto
  const response = await getAnthropic().messages.create({ model, max_tokens, system, tools, tool_choice: { type: 'auto' }, messages })
  await run.step('model', ...)                       // logged
  messages.push({ role: 'assistant', content: response.content })

  const toolCalls = response.content.filter(b => b.type === 'tool_use')
  if (toolCalls.length === 0) { /* nudge once, then fail */ continue }   // 2. no tool asked for

  for (const call of toolCalls) {                    // 3. run each tool
    output = await tool.handler(call.input)          //    (a throw becomes is_error for Claude)
    await run.step('tool_call', ...); await run.step('tool_result', ...)
    results.push({ type: 'tool_result', tool_use_id: call.id, content: JSON.stringify(output) })
  }
  if (a tool marked givesUp was called) fail the run with its reason          // 4
  if (a tool marked endsRun succeeded) { run.finish(output); return }         // 5. the answer
  messages.push({ role: 'user', content: results })  //    otherwise feed results back, loop
}
throw new Error(`No final answer after ${maxTurns} turns`)   // the guard
```
It stops in exactly four ways: `submit_recipe` succeeded (the answer), the agent gave up on purpose, something went wrong (API error, cut-off reply, model ignoring the nudge), or `maxTurns` was hit. Every one of those ends with `run.finish` or `run.fail`, so no run is left unexplained.

**The run log (`runLog.ts`)** is a header row (`AgentRun`: agent, trigger, input, status, output/error, token totals) plus ordered `AgentStep` rows. `/agent-runs` just reads them.

**Two pieces of the importer worth reading:**
- `fetch_page` → `pageText.ts`: look for `<script type="application/ld+json">`, walk it (arrays, `@graph`) for a node of type `Recipe`, keep only the useful fields. No JSON-LD: strip the HTML to its visible text.
- `submit_recipe` → `buildDraft` in `tools.ts`: the only gate between Claude and the review screen. It rejects bad drafts with a message Claude can act on, computes `amount` from the quantity text, and fills the source URL.

**One real import traced** (run `cmv57up7c00008y51innnqptf` in the local database; on 12 Oct 2026 against the JSON-LD fixture page `http://localhost:4455/jsonld.html`; open it at `/agent-runs/cmv57up7c00008y51innnqptf` on a local run, or compare with any JSON-LD import you do on the preview). 7.2 s, 3 model turns, 9 steps, 8,521 tokens in / 1,075 out.

What Claude saw on turn 1 (step 1 on the page): the system prompt ("never invent a method...", the allowed protein/carb types read from the database), the tool list (name, description and JSON schema of the four tools) and one user message: `Import the recipe at this URL: http://localhost:4455/jsonld.html`.

The run's final output is the draft plus the two "similar" recipes; the review screen shows it and only Save writes to the database.

Each turn costs more input tokens than the last (2,334, 2,968, 3,219): the whole conversation is re-sent every turn, which is also why the loop must stop (`maxTurns`).

**Other real runs** (same day, same local database, dev key):

Result "Nana Ruth's Hungarian Goulash": 11 ingredients as written ("1 kg stewing beef" notes "cut into 3cm cubes", "2 tbsp lard or sunflower oil" kept as one ingredient, "1 tsp caraway seeds"), 6 servings, 4 steps with timers (15 min and 2 h taken from the text), protein `red-meat`, no duplicates. The essay and comments were ignored.
- *Free text* ("my schnitzel: chicken breast, flatten, egg, breadcrumbs, fry 4 min a side"): 4.9 s, 2 model turns, no `fetch_page` call. "My Schnitzel": 3 ingredients with no quantities (none were given, none invented; the chicken breast got note "flattened"), 3 steps, the last with a 240 s timer, protein `chicken`, no servings or time.
- *No method* (`nomethod.html`, a Greek salad page with only ingredients, run several times): 7 ingredients ("a handful" of olives kept as text with `amount` null), servings 4, **0 steps** every time. The UI says "No method found. It will be saved without steps".
- *Unreachable page* (`https://www.bbcgoodfood.com/recipes/easy-pancakes-recipe`): first attempt (before the `cannot_import_recipe` tool existed) produced the placeholder recipe described under Decisions, after 19 steps and 18k tokens; after the fix it fails cleanly in 8 steps with "The page at that URL could not be fetched, so there is no recipe to import."

**What the SDK tool runner will do for us later (S11).** The Anthropic TypeScript SDK (0.133.0 installed) has `client.beta.messages.toolRunner({ model, max_tokens, messages, tools: [betaTool({ name, description, inputSchema, run })], max_iterations })` (also `betaZodTool` for Zod schemas). It runs steps 1 to 5 above for us: it calls the model, collects the `tool_use` blocks, calls each tool's `run`, builds the `tool_result` messages, appends them, repeats, and stops when Claude answers without asking for a tool or when `max_iterations` is reached. In `loop.ts` that replaces the whole `for` body: the `messages.create` call, the filter for `tool_use` blocks, the handler calls with try/catch for `is_error`, the `tool_result` assembly and the "push results and loop" at the bottom, and the `maxTurns` counter. What it does **not** give us, and what we keep writing ourselves: the run log (we would log from inside each `run` function, and the runner exposes each message as it iterates), a "final answer" tool (our `endsRun`: with the runner the equivalent is reading the last message or ending on a specific tool), the "give up" exit, and the nudge for a model that stops without a tool call (with the runner a plain-text reply simply ends the run). Having read this loop first is the point: the runner is these 60 lines, packaged.

## Try on the preview
Needs `ANTHROPIC_API_KEY` on the preview. Recipe pages that block automated visitors will fail with a message; that is expected.
1. Recipes page, tap **Import**, paste a recipe URL from a normal recipe site (for example a BBC Good Food or Sainsbury's recipe), tap **Import**. Wait 5 to 20 seconds. Expect a review screen with the name, servings, ingredients in the page's own units, and a numbered method. Tap **Save to recipe book**: it appears in the list (tier "New").
2. Tap **Import** again and type a family recipe in your own words (for example the schnitzel line). Expect only the ingredients and steps you described: no quantities you didn't give, no invented extra steps. Tap **Discard**: nothing is added.
3. Import a page that is just a list of ingredients, or describe a recipe with no method ("greek salad: tomatoes, cucumber, feta, olives"). Expect "No method found. It will be saved without steps" on the review screen.
4. Paste something that isn't a recipe or a URL that doesn't load. Expect a short red message, "Could not import a recipe: ...", with a "See what happened" link.
5. Open the menu, **Agent Runs**. Expect your imports newest first with status, time and tokens. Tap one: expand "Input" on the tool calls and "Output" on the results (the page text or recipe data the model saw). Tap the model turn's "Raw response" to see exactly what it sent back.

## Handoff
- **Loop API:** `runAgent<T>({ agent, trigger, input, model, maxTokens, system, userMessage, tools, maxTurns })` returns `{ runId, ok, output?, error?, gaveUpReason? }` and never throws; callers show `error`/`gaveUpReason` and link to `/agent-runs/<runId>`. A tool is `{ name, description, inputSchema, handler, endsRun?, givesUp? }`. Exactly one tool should be `endsRun`. Model name and limits come from `AI_CONFIG`, add an entry per agent.
- **Run log:** `startRun({ agent, trigger, input })` returns `{ id, step(kind, payload, { toolName, tokens }), finish(output), fail(error) }`. Step kinds: `model`, `tool_call`, `tool_result`, `note` (loop commentary). Allowed triggers: `manual | batch | schedule | mcp` (batch backfill S07 should pass `batch`). Payload shapes: model `{ content, stopReason }`, tool_call `{ id, input }`, tool_result `{ output, isError }`, note `{ text, reason }`.
- **Importer for S07 (batch backfill):** call `runRecipeImporter({ url } | { text }, 'batch')`. It returns the same `AgentResult<ImportResult>`; `output.draft` is a `RecipeDraft`, `output.similarRecipes` the duplicates it looked up. Save with `saveRecipeDraft(draft)` (re-validates; recipes it creates have tier `new`, so for backfilling existing recipes you will want to update rows instead and reuse `buildDraft` for the checks).
- **For S04 (editor):** the review view is deliberately minimal; swap it for the editor, giving it a `RecipeDraft` (ingredient `key`s are temporary, steps use `{ing:<key>}`) and posting the edited draft to `/api/recipes/import/save`. If the editor works with saved ids instead, call the save route first and open the saved recipe in the editor.
- **For S06 (discovery in Claude.ai/MCP) and later agents:** `lib/agents/recipeImporter/safeFetch.ts` (`safeFetchHtml`) is the place to fetch any user-supplied URL; do not call `fetch` on user URLs directly. `lib/agents/recipeImporter/pageText.ts` (JSON-LD first, then text) is reusable.
- **Env:** `ALLOW_PRIVATE_FETCH=1` only for local dev and tests (ignored in production). The sandbox cannot reach external sites; serve fixtures locally.
- **Cost guard:** `maxTurns` 8; each real import cost 3 to 5 model turns and 5k to 9k input tokens.
- **Tests:** unit tests for the loop (stops on the final tool, respects `maxTurns`, records every step in order, tool errors, nudge, give-up, `max_tokens`, API error), run log, each tool, safe fetch (private-address table, redirects, dev flag in production), page text, save, routes and the modal; integration tests (`tests/integration/recipe-importer.integration.test.ts`) with scripted Claude against real Postgres.
- **Old imports of `ExtractedRecipeData` and `EXTRACT_RECIPE_SCHEMA` are gone** (types and `lib/ai/schemas.ts`).
